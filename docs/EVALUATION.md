# 成效評估：KPI、基準與前後比較

對應審查報告第 6 層「實際成效」的 IMP-01（沒有成效指標與基準）與 IMP-02（以前後比較取代 A/B Test）。

> 本文件與之後的量測紀錄**不記錄代號、股數、金額或任何個人資料**（repo 與 Actions log 都是公開的），只記錄時間、次數與比例。

## 1. 要評估什麼

專案目的是「快速掌握資產狀況，並依五線譜 / VIX / Forward P/E 做決策」。對應到可量測的成效：

- 頁面上的數字**夠新**（快照新鮮度）且**正確**（報價正確率）；
- 資料出錯時**系統比使用者先發現**（自動偵測比例），而且**修得快**（MTTR）；
- 使用者**很快拿到答案**（取得答案時間）。

## 2. 評估設計（取代 A/B Test）

個人工具只有一位使用者，沒有對照組，改用 **within-subject 前後比較**：

| 階段 | 期間 | 說明 |
|------|------|------|
| 基準期（before） | 2026-10-31 ～ 2026-11-24（25 天） | 回溯自 `PROMPT.md`、git log 與 GitHub Actions 紀錄（見第 3 節） |
| 介入 | 這批修正部署上線，且外部觸發排程與監控（README「排程與監控」）設定完成的那一天 | 部署前測試與資料品質閘門、報價共識修正、分割處理、新鮮度顯示、外部觸發、監控 |
| 觀察期（after） | 介入日起連續 4 週 | 依第 5 節的方法量測第 4 節的 KPI |

規則：

- KPI 定義、目標與量測方式**事先定好**（第 4 節），觀察期間不更改；必須更改時，觀察期重新起算 4 週。
- 觀察期內發生的異常事件（休市、分割、來源改版、GitHub 大規模延遲、觸發機器關機等）逐筆記錄在第 7 節備註，判讀時另外說明，不從資料中刪除。

## 4. KPI 與目標

| KPI | 定義 | 目標 | 量測（第 5 節） | 頻率 |
|-----|------|------|-----------------|------|
| 快照新鮮度 P95 | 任一時刻線上快照的年齡（該時刻 − 快照的 `generatedAt`） | **≤ 60 分鐘** | 5.1 | 每週 |
| 報價正確率 | 收盤後快照價格與官方收盤價偏差 ≤ 0.5% 的檔數比例 | **≥ 99%** | 5.2 | 每週抽 1 個台股、1 個美股交易日 |
| 使用者發現的資料錯誤 | 使用者先發現、系統沒有攔下的資料錯誤次數 | **≤ 1 次 / 月** | 5.3 | 每週 |
| 自動偵測比例 | 系統先攔下（部署閘門 ERROR、監控告警）的資料錯誤 ÷ 全部資料錯誤 | **≥ 75%** | 5.3 | 每週 |
| MTTR | 回報或攔下 → 修正後第一次成功部署 | **≤ 1 小時**（含驗證） | 5.3 | 每次事件 |
| 取得答案時間 | 開頁到能回答「今天總資產與配置？」 | **≤ 30 秒** | 5.4 | 每週 1 次 |

**改善門檻**（事先定好）：

- 使用者發現的資料錯誤比基準減少 ≥ 75%：4 次 / 25 天 → 觀察期 4 週內 **≤ 1 次**。
- 快照新鮮度 P95 從約 7 小時（平均）降到 **≤ 60 分鐘**。
- 其餘 KPI 以上表目標判定；基準未量測的（報價正確率、取得答案時間）只看是否達標。

## 5. 量測方式

### 5.1 快照新鮮度與排程執行率

用 GitHub CLI 取部署紀錄，每 10 分鐘取樣一次「當下線上的快照有多舊」：線上快照 = 該時刻之前最後一次完成的成功部署，年齡以該次執行的建立時間近似 `generatedAt`（略為高估，偏保守）。

```bash
gh run list --workflow deploy.yml --status success --limit 2000 --json createdAt,updatedAt > /tmp/deploy-runs.json
python3 - /tmp/deploy-runs.json 2026-12-01 2026-12-29 <<'EOF'
import bisect, datetime as dt, json, sys
tpe = dt.timezone(dt.timedelta(hours=8))
ts = lambda s: dt.datetime.fromisoformat(s.replace("Z", "+00:00"))
runs = sorted((ts(r["updatedAt"]), ts(r["createdAt"])) for r in json.load(open(sys.argv[1])))
done = [finished for finished, _ in runs]
t, end = (dt.datetime.fromisoformat(d).replace(tzinfo=tpe) for d in sys.argv[2:4])
ages = []
while t < end:
    i = bisect.bisect_right(done, t) - 1
    if i >= 0:
        ages.append((t - runs[i][1]).total_seconds() / 60)
    t += dt.timedelta(minutes=10)
ages.sort()
print(f"樣本 {len(ages)}，P50 {ages[len(ages) // 2]:.0f} 分鐘，P95 {ages[int(len(ages) * 0.95)]:.0f} 分鐘")
EOF
```

日期換成觀察期的起訖（台北時間，迄日不含）。排程執行率（`createdAt` 是 UTC 字串）：

```bash
gh run list --workflow deploy.yml --limit 2000 --json event,createdAt \
  --jq '[.[] | select(.createdAt >= "2026-12-01") | .event] | group_by(.) | map({(.[0]): length}) | add'
```

`schedule` 是內建排程、`workflow_dispatch` 是外部觸發（或手動）、`push` 是推送觸發；觀察期每小時至少應有一次 `schedule` 或 `workflow_dispatch`。

### 5.2 報價正確率

目前沒有自動化，抽樣人工比對：

1. 收盤後（台股 14:30 後；美股收盤後）在本機執行 `python build_static.py --output <暫存路徑>/index.html`，或使用當時的線上頁面。
2. 每檔非現金持股的價格與官方收盤價比對：台股以證交所 / 櫃買中心每日收盤行情為準；美股以交易所公布的收盤價為準（Yahoo 是報價來源之一，用它比對不算獨立驗證）。
3. 只記錄「偏差 ≤ 0.5% 的檔數 / 總檔數」，**不記錄代號與價格**；比對完刪除暫存檔。

### 5.3 資料錯誤、自動偵測與 MTTR

每次發現資料錯誤（不論誰先發現）記一筆，放在 repo 以外的私人紀錄，或開一個不含代號、金額的 Issue：

| 欄位 | 內容 |
|------|------|
| 發現時間 | 台北時間 |
| 發現者 | 使用者 / 部署閘門 / 監控 |
| 類型 | 報價、匯率、歷史、分割、市場指標、借貸 |
| 修正部署時間 | 修正後第一次成功部署的時間（`gh run list`） |

- 部署閘門攔下的紀錄：失敗的 `deploy.yml` 執行中，失敗步驟是「Data quality gate」的那些（`gh run view <run id> --json jobs --jq '.jobs[].steps[] | select(.conclusion == "failure") | .name'`）。只算真的資料錯誤；閘門門檻太嚴造成的誤擋另外記錄，不算進自動偵測。
- 監控告警：`scripts/check_deploy_age.py --issue` 開的 Issue（資料太舊屬新鮮度問題，不算資料錯誤，但要記在備註）。

### 5.4 取得答案時間

每週一次，從點開書籤到說出「總資產多少、原型:槓桿:現金比例」計時，記錄秒數。

## 6. 判讀與限制

- **樣本很小**：基準只有 4 次錯誤，相差 1 次也可能是運氣。結論只用來判斷「這批修正是否值得保留、下一步先做什麼」，不做統計檢定。
- **自動偵測比例在基準期必然是 0**（當時沒有閘門），提升有一部分是定義使然；要同時看「使用者發現的資料錯誤」是否真的下降。
- **外在因素**：市場事件（分割、休市）、來源網站改版、GitHub 排程負載、外部觸發機器的開機時間都會影響結果。新鮮度 KPI 不達標時，先確認外部觸發是否在執行，再判斷是不是程式問題。
- **觀察者效應**：使用者看頁面的頻率會影響「使用者發現的錯誤」；觀察期內維持平常的使用習慣。
